# 火山方舟 Seedance 2.5 用量治理平台设计

- 日期：2026-08-31
- 状态：已确认，可进入实施计划
- 建设方式：优先复用 New API，先 POC，后生产化
- 建设范围：独立的公司级内部平台，不接入现有汽车广告项目

## 1. 摘要

公司当前使用一个火山方舟总账号。需要使用 Seedance 2.5 的人员会获得一把真实方舟 API Key，并直接调用火山方舟。现有方式不能可靠、及时地按 Key 统计用量和费用，也不能在调用前实施统一额度控制。

最终目标是在公司云服务器部署一个中转平台，实施时先在 Windows 开发电脑完成本机 POC。真实方舟 Key 作为一个上游渠道凭证，管理员在同一个内部服务账号下为预计约二十名使用者分别签发平台虚拟 Key。所有请求必须经过中转平台；平台负责鉴权、按 Key 归属用量、额度预占、异步任务跟踪、最终结算、退款、日志和管理后台，火山方舟官方数据用于汇总核对。

平台不从零开发。首选基线为 New API `v1.0.0-rc.29` 当前指向的提交 `2b6f1dfefbe217fed31fc0726717cc7de6958e8e`，因为该提交已经提供 Seedance 2.5 任务插件、虚拟 Token、渠道、异步任务、原子配额预占与日志能力。实施时以完整提交哈希为准，不只依赖可能变化的标签或 `latest`。该版本的插件系统仍属实验性，官方不建议直接用于生产，因此必须先完成隔离 POC 和完整账务验收。

## 2. 背景与问题

### 2.1 当前方式

1. 公司拥有一个火山方舟总账号。
2. 管理员在方舟控制台创建真实 API Key。
3. 每位使用者获得一把真实 Key，并直接访问方舟 Seedance 2.5。
4. 所有费用最终归集到同一公司账号。

### 2.2 当前问题

- 官方用量和账单主要用于账号、项目或接入点维度的聚合核对，不能作为公司内部按人的实时主账本。
- 无法在请求到达方舟前执行单人额度、停用、过期和模型权限控制。
- 异步视频任务的创建、轮询、成功、失败、取消和退款缺少公司侧统一状态。
- 无法稳定回答“某把 Key 在某段时间用了多少、产生了什么任务、花费多少、是否已经结算”。

## 3. 已确认需求

### 3.1 使用范围

- 仅供公司内部使用。
- 预计约二十名使用者，短期内不按大规模多租户系统设计。
- 仅管理员登录控制台；普通使用者只持有虚拟 Key。
- 不为普通使用者创建账号或操作页面；所有虚拟 Key 归属于同一个内部服务账号。
- 公司可以在使用方程序中统一配置中转 Base URL。
- 第一阶段只管理火山方舟 Seedance 2.5。
- 当前验收只覆盖文生视频；图像输入和视频输入均延后，未来启用时另做完整能力与计费验收。

### 3.2 凭证策略

- 现有真实方舟 Key 可以统一停用并替换为虚拟 Key。
- 真实方舟 Key 仅作为服务器端上游渠道凭证。
- 平台不负责创建、删除、轮换或展示单个真实方舟 Key。
- 管理对象仅为平台虚拟 Key。
- 所有需要纳入统计的调用必须经过公司中转地址。

### 3.3 数据与费用边界

- 只统计平台上线后经过中转站的请求。
- 不导入、不补算旧真实 Key 的历史用量。
- 第一期不自动清理上线后的任务与用量日志；预计约二十人的元数据量较小，后续只有在数据库增长明显时再制定归档周期。
- 不加价，不设置部门倍率或内部利润。
- 费用按方舟实际 usage 和官方价格规则计算。
- 管理界面和任务记录必须区分预估、预占和任务完成后的实际费用；与方舟官方账号数据的核对由管理员在两个后台之间手工完成。
- 官方账单存在延迟，平台不得把实时预估值标记为“官方已结算账单”。

### 3.4 额度设置

- 管理员直接使用 New API 现有 Token 编辑功能设置单个虚拟 Key 的剩余额度。
- 第一期采用“设置为指定余额”的绝对值操作，不开发 `+¥100` 式增量充值、人工扣减、冲正或独立充值流水。
- 额度只改变虚拟 Key 在中转站中的可消费上限，不改变火山方舟账号余额。
- 管理页面只显示人民币，不向管理员暴露 New API 原始 quota 点数。
- 内部换算固定为 `500,000 quota = ¥1`，即 `1 quota = ¥0.000002`。例如设置 `¥100` 等价于内部 `50,000,000 quota`。
- 换算只改变内部展示与配额表示，不改变 Seedance 的方舟官方价格。
- 管理员不得在某把 Key 仍有未完成任务时直接覆盖其剩余额度。标准操作顺序为：停用 Key 阻止新任务、等待在途任务全部结算、设置新余额、重新启用 Key。

### 3.5 Key 生命周期

- 虚拟 Key 默认永久有效，由管理员手动停用或删除。
- 日常回收优先停用，保留历史任务和用量记录。
- 只有 Key 已停用、没有未完成任务且确认不再需要历史查询时才删除。

### 3.5 明确不做

- 不接入现有汽车广告项目。
- 不建设公开 API 售卖平台。
- 不建设部门、团队、部门管理员或内部结算层级。
- 不建设普通使用者后台。
- 不启用在线支付、兑换码、邀请返利或订阅套餐。
- 不开发充值、人工扣减、冲正和余额调整审计系统。
- 不管理真实方舟 Key 的生命周期。
- 不追溯上线前历史数据。

## 4. 目标与成功标准

平台上线后应满足：

1. 每位使用者获得独立虚拟 Key，真实方舟 Key 不再暴露。
2. 每个视频任务能够唯一归属到一把虚拟 Key。
3. 管理员能够按 Key 查询任务、用量、人民币费用、已用额度和剩余额度。
4. Key 的停用、过期、模型限制和额度不足能够在调用方舟前生效。
5. 成功任务只结算一次；失败、取消、超时和不确定状态有明确账务规则。
6. 服务重启后可以继续跟踪未完成任务，不丢失或重复结算。
7. 所有虚拟 Key 的汇总用量可以与方舟官方账号总用量核对。
8. 平台优先通过配置和现有功能实现；只有验证确定缺失的能力才二次开发。
9. 同一 Key 并发提交时不能超过其剩余额度，余额不得变为负数。

## 5. 术语

- **真实方舟 Key**：由火山方舟签发、能够直接调用方舟的上游凭证。
- **虚拟 Key / Token**：由公司中转平台签发、只能调用公司中转地址的凭证。
- **公开任务 ID**：返回给虚拟 Key 使用者的中转平台任务标识。
- **上游任务 ID**：火山方舟返回的真实任务标识，仅管理员和内部任务系统可见。
- **原始 quota**：New API 内部使用的整数额度点；本项目按 `500,000 quota = ¥1` 换算且不在管理页面展示。
- **预估费用**：提交前根据模型、时长、分辨率和输入类型计算的人民币估算金额。
- **预占费用**：任务执行期间从虚拟 Key 可用额度中冻结的金额。
- **实际费用**：任务达到终态后，根据方舟返回的实际 usage 和价格版本计算的金额。
- **官方核对**：平台汇总用量与方舟官方用量或账单进行的事后比较。

## 6. 方案比较与选择

### 6.1 New API

优势：

- 原生提供用户、虚拟 Token、额度、渠道、模型限制、IP 白名单、日志和管理后台。
- `v1.0.0-rc.29` 已包含 `doubao-seedance-2-5-260628` 任务插件。
- 已具备异步任务持久化、预扣、完成结算、退款和轮询框架。
- Docker 部署简单，适合约二十人规模内部使用。

风险：

- `rc.29` 仍是候选版本。
- 实验性插件系统从 `rc.27` 才开始引入。
- `rc.28` 曾出现数据库迁移兼容性回归。
- 官方明确说明该版本仍不建议用于生产。
- 使用 AGPLv3，并包含署名和原项目链接保留要求。

结论：作为首选 POC 基线，但未经账务、安全和恢复验收不得直接生产上线。

### 6.2 LiteLLM Proxy

优势：虚拟 Key、预算、用户和管理 UI 较成熟。

不足：未发现火山方舟 Seedance 异步视频的完整原生适配。通用透传不能自动完成任务归属、预占、最终 usage 结算和退款，需要开发关键账务逻辑。

结论：作为 New API 无法通过 POC 时的第二选择。

### 6.3 Higress + OpenMeter

优势：网关、鉴权、计量和账本职责边界清晰，适合多供应商和更大规模。

不足：需要组合多个组件并自行开发控制面胶水。对约二十人、单供应商场景工程量过大。

结论：当前不采用；只有未来扩展为多供应商企业网关时再评估。

## 7. 总体架构

```text
使用者程序
  ↓ Authorization: Bearer <虚拟 Key>
公司中转地址（POC HTTP；生产 HTTPS）
  ↓
New API
  ├─ 虚拟 Key 鉴权与额度
  ├─ Seedance 任务插件与轮询
  ├─ 管理员控制台
  ├─ 用量、日志和任务结算记录
  └─ PostgreSQL（权威数据源）
     Redis（可选扩展）
  ↓ Authorization: Bearer <真实方舟 Key>
火山方舟 Seedance 2.5
```

### 7.1 组件

- 反向代理：生产阶段负责 TLS 终止和请求体上限；简化 POC 阶段可以暂不部署。
- New API 单实例：控制台、虚拟 Token、渠道、任务和账务。
- PostgreSQL：用户、Token、任务、日志和账务权威数据源。
- Redis：可选扩展，用于缓存、共享限流和多实例共享状态。预计约二十人、单实例的 POC 和第一期生产环境默认不部署。
- 火山方舟渠道：保存真实 Key、模型和上游 Base URL。
- 备份任务：定期备份 PostgreSQL、必要配置和加密密钥。

不部署 Redis 时，会话校验更多地访问 PostgreSQL，限流计数保存在单实例内存中并在服务重启后重置；这不影响虚拟 Key、任务、日志和账务数据持久化。Redis 不作为余额或结算账本，额度扣减、幂等结算和防并发超扣必须由 PostgreSQL 事务、条件更新和唯一约束保证。New API 的 `BATCH_UPDATE_ENABLED` 必须关闭，避免额度延迟批量写入。

### 7.2 API 入口

POC 使用 New API 现有 Seedance 插件路径：

- 创建：`POST /doubao/api/v3/contents/generations/tasks`
- 查询：`GET /doubao/api/v3/contents/generations/tasks/{task_id}`

使用者程序由公司统一将原方舟 Base URL 改为中转地址的 `/doubao`，并把真实方舟 Key 替换为虚拟 Key。本机 POC 使用 `http://localhost:3000/doubao`；迁移到云服务器后，临时联调可以使用服务器 IP，长期运行时再切换为 `https://公司域名/doubao`。

第一阶段不要求增加裸 `/api/v3/...` 路由别名；只有现有客户端无法配置 `/doubao` Base URL 时才增加别名，并继续复用同一鉴权、任务和账务链路。

## 8. 管理员功能

### 8.1 管理后台原则

- 完整复用 New API 自带管理员控制台，不建设独立前端看板。
- 复用现有统计、Token、日志、任务和渠道页面；通过 Token 名称和日志筛选查询单 Key 数据。
- 用量日志保留调用时间、Token 名称、模型、计费 Token、扣除额度、人民币费用和状态；不为本需求额外记录完整提示词或素材正文。
- 隐藏或关闭注册、普通用户工作台、在线支付、订阅、兑换码、邀请、聊天、绘图和多分组等无关入口。
- 只有现有配置不能实现人民币显示或必要入口精简时，才做最小前端修改。

### 8.2 虚拟 Key 管理

每把 Key 展示：

- 名称和使用人备注。
- 脱敏后的 Key。
- 启用、停用和过期状态。
- 已用额度和剩余额度，均显示为人民币。
- 创建时间、有效期和最后调用时间。
- 调用次数、成功率和累计费用。

管理员可执行：

- 创建时复制、轮换/重置、停用和按规则删除。
- 直接设置剩余额度。
- 设置余额时执行“停用、等待在途任务结算、设置、重新启用”的操作顺序。
- 默认永久有效，必要时设置有效期。
- 限定只能调用 Seedance 2.5。
- 设置 IP 白名单。
- 查看该 Key 的任务和调用日志。

### 8.3 Key 详情

- 按日用量和费用趋势。
- 当前余额和累计消耗。
- 任务的预占、结算与失败退款结果；不提供独立人工余额流水。
- 模型、分辨率、时长、输入类型、状态和最终费用。
- 公开任务 ID、上游任务 ID和请求时间。
- 错误信息和失败原因。

### 8.4 上游渠道

- 方舟渠道状态和模型配置。
- 脱敏展示真实方舟 Key。
- 模型价格和计量规则。
- 渠道成功率及最近异常。

## 9. 功能复用边界

### 9.1 直接复用

- 管理后台。
- 单个内部服务账号及其多把虚拟 Token。
- 渠道管理。
- Token 额度、有效期、模型限制和 IP 白名单。
- 调用日志和统计图表。
- Seedance 异步任务框架。
- 预扣、完成结算和失败退款基础能力。

### 9.2 通过配置实现

- 仅启用 Seedance 2.5。
- 配置方舟真实 Key 和上游地址。
- 配置官方价格、`500,000 quota = ¥1` 换算和人民币显示。
- 关闭公开注册、第三方登录、支付、兑换码、邀请和订阅。
- 配置任务轮询、超时和日志保留策略。

### 9.3 原子配额实现复核

固定提交 `2b6f1dfefbe217fed31fc0726717cc7de6958e8e` 已在 `model/quota_reserve.go` 提供 `TryReserveTokenQuota`。无 Redis 路径使用 PostgreSQL 原子条件更新：

```sql
UPDATE tokens
SET remain_quota = remain_quota - :cost,
    used_quota = used_quota + :cost
WHERE id = :id
  AND remain_quota >= :cost;
```

只有受影响行数为 `1` 才允许请求发送到方舟；为 `0` 时按额度不足拒绝。`service/quota.go` 的 `PreConsumeTokenQuota` 已调用该原子入口，上游同时提供 `model/quota_reserve_test.go` 覆盖无 Redis 预占、余额不足及缓存路径。

因此第一期不重复开发 Token 原子扣费补丁。实施时必须：

- 检出并验证完整提交哈希，而不是仅相信版本标签。
- 保持 Redis 未配置且 `BATCH_UPDATE_ENABLED=false`。
- 运行上游 `quota_reserve` 测试，并执行真实 HTTP 并发验收。
- 如果固定提交缺少上述文件、测试失败或 HTTP 并发仍发生透支，立即停止上线并重新评估最小补丁，不能退回旧的先查后扣逻辑。

### 9.4 仅在 POC 证明缺失时开发

- 人民币符号、精度或隐藏原始 quota 的最小界面调整。
- 不确定任务的人工确认入口。
- 裸 `/api/v3/...` 路由别名。

禁止通过通用字节透传绕过 Token 鉴权、任务持久化、预扣和最终结算。

## 10. 账务模型

### 10.1 配额与任务结算

- 管理员通过现有 Token 编辑页面直接设置剩余额度，不维护自定义充值账本。
- 任务提交时由 New API 预占额度；成功后按方舟返回的实际 usage 和官方价格结算，多余预占退回。
- 对当前文生视频范围，插件按分辨率档位最大像素数和实测终点帧预估，目标是预占金额不低于最终实际金额。
- 失败、取消或超时是否产生费用，以方舟返回的实际 usage 为准。
- 如果方舟终态没有返回可用于精确结算的实际 usage，POC 必须将其标记为验收失败，不能把预估值伪装为实际账单。
- 如果任一合法的第一期请求出现最终实际费用高于预占金额，也视为验收失败；必须先修正保守预占公式，不能依赖任务完成后的超额扣款突破 Key 硬额度。
- 单个内部服务账号的总额度设置得足够高，使单 Token 额度成为实际限制条件；按 Key 的统计以 Token 和任务日志为准。

### 10.2 任务费用状态

任务金额状态依次为：

1. `estimated`：完成参数解析，尚未冻结额度。
2. `reserved`：额度已预占。
3. `settled`：根据方舟实际 usage 结算。
4. `reconciled`：平台汇总已经与方舟官方账号数据核对。

单个任务只能从未结算进入一次最终结算。结算使用唯一任务键和数据库原子更新，重复轮询不得重复扣费。

### 10.3 价格版本

- New API `v1.0.0-rc.29` 的模型同步只同步模型元数据，不会自动同步火山方舟 Seedance 官方价格。
- 第一期由管理员根据火山方舟官方价格手工配置 Seedance 2.5，不开发自动价格同步。
- 上线前及方舟发布调价后，管理员必须核对价格配置，并通过真实任务验证一次平台费用。
- 费用计算使用任务提交时生效的价格；修改价格只影响修改后提交的任务。
- 历史任务保留已经结算的实际额度和费用，不因后续价格变化重新计算。
- POC 必须核对 Seedance 2.5 不同分辨率和时长的价格配置；输入类型在未来启用对应能力时再核对。
- POC 根据方舟 Seedance 2.5 的真实参数校验结果锁定允许的时长和分辨率范围；不得直接沿用插件协议层允许的超大时长上限。

### 10.4 官方核对

- 平台按虚拟 Key 保留任务和调用日志。
- 方舟官方用量只用于账号总量的小时或日级核对。
- 核对维度至少包含时间段、模型、总 usage、任务数和总费用。
- 第一期由管理员按相同时间段手工比较 New API 汇总与方舟控制台数据，不开发自动核对页面或差异记录系统。
- 不一致时不自动修改历史账务。
- 第一期不提供人工冲正；管理员只查看并分析差异，修正错误的价格或程序后重新验证。

## 11. 任务流程与异常处理

### 11.1 正常流程

1. 校验虚拟 Key 状态、有效期、模型权限和余额。
2. 根据请求参数计算保守预估费用。
3. 使用 PostgreSQL 条件更新原子预占额度。
4. 使用真实方舟 Key 提交任务。
5. 保存虚拟 Key、公开任务 ID、上游任务 ID和价格版本。
6. 后台轮询任务。
7. 成功后按实际 usage 结算；实际费用低于预占时退回差额，实际费用高于预占则记为异常并阻止生产验收通过。
8. 写入任务结算结果和调用日志。
9. 后续执行官方汇总核对。

### 11.2 异常规则

- Key 无效、停用、过期或额度不足：本地拒绝，不调用方舟，不扣费。
- 同一 Key 的并发预占只有余额足够的请求可以成功，其他请求本地拒绝，余额不得为负数。
- 上游参数校验失败且未创建任务：释放全部预占。
- 上游已返回任务 ID：必须持久化后才能向客户端确认成功。
- 提交超时且结果不确定：标记为 `unknown`，不得自动重复提交或立即退款。
- 临时查询失败：退避重试，不改变账务终态。
- 成功：按实际 usage 幂等结算。
- 失败、取消或过期：若方舟返回计费用量则按实际用量结算，否则退款。
- 服务重启：从 PostgreSQL 恢复所有非终态任务。
- 官方数据不一致：生成差异记录，等待管理员审核。

### 11.3 任务隔离

- 使用者只能用创建任务时的虚拟 Key 查询对应公开任务 ID。
- 不返回其他 Key 的任务存在性。
- 上游任务 ID 不作为公开授权凭据。
- POC 必须测试跨 Key 查询、枚举和直接使用上游 ID 的情况。

## 12. 基础安全与运行边界

- 本机 POC 只通过 `localhost:3000` 访问，不要求域名、HTTPS 或公网开放。
- 迁移云服务器后的临时联调允许通过公网 `服务器IP:3000` 访问；管理员知晓 HTTP 会明文传输登录凭证和虚拟 Key。
- 生产长期运行时配置域名和 HTTPS，但不要求限制为公司网络、VPN 或固定 IP，管理后台允许正常公网访问。
- 关闭公开注册和不需要的认证方式。
- 管理员使用强密码；现成版本支持时开启双因素认证。
- 真实方舟 Key 只在本机或服务器的 New API 渠道中配置，不写入设计文档、聊天、日志和代码仓库。
- 虚拟 Key 创建后交给对应使用者，并可由管理员停用或轮换。
- 日志不得记录完整真实 Key、虚拟 Key、Authorization 头或敏感媒体签名地址。
- 数据库、加密密钥和配置分别备份。
- 升级前备份数据库，并在测试环境完成账务回归。
- 固定完整源码提交或镜像摘要，不使用 `latest` 或仅依赖可移动标签自动滚动升级。
- 持续关注 New API 安全公告，视频任务越权属于上线阻断级问题。

## 13. 部署与运维

### 13.1 POC

- 第一阶段先在当前 Windows 开发电脑本机运行成功，不直接部署云服务器。
- 本机使用 Docker Desktop、WSL2 后端和 Docker Compose；当前电脑尚未安装或尚未提供可用的 `docker` 命令，开始实施前需要完成环境准备，安装过程可能要求管理员权限和重启。
- 检出 New API 提交 `2b6f1dfefbe217fed31fc0726717cc7de6958e8e` 并从该源码构建本地镜像；记录生成的镜像摘要。
- PostgreSQL。
- 默认不部署 Redis，保留后续通过配置接入的能力。
- 通过 `http://localhost:3000` 验证，域名、HTTPS 和服务器配置不阻塞本机 POC。
- 本机阶段暂不配置自动备份。
- 与正式方舟调用环境隔离。

### 13.2 云服务器迁移与生产门槛

本机 POC 全部通过后，再把同一套 Docker Compose 配置迁移到已有 Linux 云服务器。服务器阶段执行：

- PostgreSQL 每天自动执行一次 `pg_dump`，保留最近 7 天。
- 开启云厂商自动云盘快照，防止服务器或云盘整体故障。
- 域名和 HTTPS 可以在服务器功能联调完成后配置，但长期运行前必须完成。

满足以下任一条件后才考虑生产：

1. New API 发布已明确推荐生产使用的稳定版本，且 POC 账务回归通过；或
2. 公司接受固定 RC 版本并自行维护其安全、迁移和账务风险，且完整 POC 通过。

生产环境继续使用单实例即可，不引入 Kubernetes、多节点或 ClickHouse。数据库定期备份，升级前完成恢复演练。只有出现多实例部署、脚本高并发或高频轮询、数据库缓存压力，或者需要跨实例共享限流状态时，才增加 Redis。

## 14. POC 计划

### 14.1 基础配置阶段

- 部署由固定提交 `2b6f1dfefbe217fed31fc0726717cc7de6958e8e` 构建的 New API 和 PostgreSQL。
- 创建管理员并关闭无关功能。
- 配置方舟渠道但不提交生成任务。
- 创建两把测试虚拟 Key。
- 验证 Key 创建、停用、过期、额度、模型限制和 API 路由。
- 检查任务、日志、账务和价格配置的数据结构。
- 验证管理员可以按人民币设置单 Key 剩余额度，页面不暴露原始 quota。

### 14.2 真实调用阶段

用户已经明确授权在本项目 POC 中进行必要的真实方舟付费测试，不设置测试费用上限。真实 Key 仍只能通过本机 New API 渠道配置提供，不写入代码和文档。

- 使用两把虚拟 Key 测试文生视频；图像输入和视频输入当前不启用。
- 覆盖 720p 和 1080p；视频转视频、首尾帧等当前未使用能力不纳入第一期验收。
- 验证任务和费用隔离。
- 验证跨 Key 查询被拒绝。
- 验证预占、成功结算和差额退回。
- 验证额度不足和停用立即拦截。
- 给一把 Key 只保留一次任务额度，并发提交 10～20 个创建请求，验证只有额度允许的请求到达方舟且余额不为负数。
- 验证 Seedance 2.5 的合法时长边界，以及非法、超长请求被拒绝后预占额度完整退回。
- 对每种合法测试场景比较预占和最终实际费用，确认实际费用不高于预占。
- 在任务执行中重启服务，验证恢复和单次结算。
- 验证失败、取消、超时和不确定状态。
- 等待官方用量生成后核对平台汇总。

### 14.3 验收标准

- 无跨 Key 数据泄露。
- 无重复扣费、无无法解释的退款。
- 每个任务可追踪到虚拟 Key 和上游任务 ID。
- 每把 Key 的任务、已用额度和剩余额度可解释。
- 设置单 Key 剩余额度后，任务预占和结算结果正确。
- 平台汇总 usage 与方舟官方 usage 一致。
- 金额差异只能来自已确认的官方舍入规则。
- 停用和额度限制能够可靠阻止新任务。
- 服务重启不会丢失任务。
- Seedance 2.5 不同计费参数的价格配置正确。
- 原子预占直接使用固定提交已有实现；除 POC 证明人民币展示确实缺失外，不修改 New API 核心功能。

任一账务、隔离、恢复或价格验收失败，都阻止生产上线。
