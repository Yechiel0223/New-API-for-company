# 双员工账号 + 独立虚拟 Key：Seedance 2.5 真实验收记录

> 测试日期：2026-09-01（Asia/Shanghai）
> 测试环境：本机 Docker Compose，New API + PostgreSQL，无 Redis
> 模型：`doubao-seedance-2-5-260628`
> 结论对象：每个员工一个 New API 普通用户账号、一个独立虚拟 Key；所有员工共用同一个火山方舟渠道和真实 Key
> 安全约束：本文不记录任何真实 Key、虚拟 Key 明文、账号密码、会话令牌、数据库密码或带签名的视频 URL。

## 1. 先看结论

本轮已经用两个真实员工账号、两把独立虚拟 Key 和同一个火山方舟渠道完成 5 个付费视频任务。结果证明：

1. **“每名员工一个普通用户账号 + 一个虚拟 Key + 共用一个真实方舟渠道”方案可行。**
2. 员工不需要操作 New API 页面，只需要拿到自己的虚拟 Key 和公司统一 Base URL。
3. Root/管理员可在用户、日志和用户统计页面统一查看所有员工的余额、用量、模型、Key 名称和调用记录。
4. 每个员工的最终费用都落到自己的用户钱包、自己的虚拟 Key 和自己的任务记录；Root 自己的余额没有被员工调用扣减。
5. 不同员工无法用自己的 Key 查询另一名员工的异步视频任务，跨账号双向查询均返回 404。
6. 余额不足的合法请求在创建方舟任务前被本地 403 拒绝，不产生上游任务和费用。
7. 5 个视频任务全部成功，最终费用都与 `actual completion_tokens × 对应人民币单价` 相符。

本轮不是“所有项目全部通过”：

- 省略 `ratio`、使用默认自适应比例时，一次 1080p/5 秒任务的 actual usage 比预扣多 363 tokens，即多结算 ¥0.020124。**最终账单准确，但预扣不再是绝对上限。**
- 管理员通用日志页面顶部的“用量”汇总显示 ¥0，即使下方已有消费日志；日志明细本身正确。
- `quota_data` 聚合没有扣除 480p 任务的极小退款，使员工 A 的统计聚合比任务权威账本多 ¥0.000056；当前两次同类退款使全局聚合多 ¥0.000112。

因此：

- 对“按员工归属、查看真实最终费用和日志”这个核心需求，方案通过。
- 若公司只统计用量、不把员工余额当作严格停机线，当前预扣偏差不影响最终费用准确性。
- 若以后要求“余额绝不能透支一分钱”，上线前需固定/校验视频比例，或给预扣增加经过验证的安全余量。
- 2026-09-01 官方 Token 与金额已完成对账；需求方同时明确接受 2026-08-31 的现有 Token 与本地账本证据，**账单与 Token 准确性验收已收口**。

## 2. 为什么要做这轮测试

此前 POC 使用同一 Root 用户下的多把虚拟 Key，可以按 Key 统计，但普通管理员无法自然地把 Root 私有数据当作员工资产管理。新方案改为每名员工一个普通用户账号，可以直接复用 New API 已有的用户额度、用户统计、全局日志和管理员权限。

本轮必须回答以下问题：

| 编号 | 要回答的问题 | 验收条件 |
| --- | --- | --- |
| A | 两个员工能否共用一个真实方舟渠道 | 两把虚拟 Key 都能成功生成视频，渠道只有一份 |
| B | 用量能否准确归属员工 | 每个任务只增加对应用户/Key 的 used quota |
| C | 管理员能否统一查看 | 用户页、全局日志和用户统计页都出现两名员工 |
| D | 账单是否仍按 actual usage 结算 | 最终人民币 = actual tokens × 档位单价，允许最多一个 raw quota 的舍入差 |
| E | 员工任务是否隔离 | 交叉查询均为 404，且不泄露 usage/视频字段 |
| F | 额度能否阻止超额调用 | 合法但余额不足的请求本地 403，任务数、渠道用量和余额均不变 |
| G | 改为员工账号后是否影响既有 Root 账本 | Root 余额/已用不变，渠道全局累计增加 |

1. Root 在 `/users` 创建普通用户。
2. Root 给该用户增加测试额度 ¥100。

5. 所有虚拟 Key 继续由 New API 路由到既有方舟渠道 #1，不为每个员工重复配置真实方舟 Key。

生产录入 20 人时，这个流程可以后续做一个管理员批量脚本；本轮没有扩大开发范围，先用平台现有能力验证数据模型。

## 10. 发现的问题与影响

### 10.1 `EMP-BILLING-001`：默认自适应比例可使 actual 高于预扣

**状态：FAIL（严格预扣上限）；PASS（最终账单准确）。**

同一员工、同一模型、同一提示词、同一 1080p/5 秒参数：

| 请求 | actual tokens | 预扣 | 最终 | 差额 |
| --- | ---: | ---: | ---: | ---: |
| 未指定 `ratio` | 245,388 | ¥13.584186 | ¥13.604310 | 补扣 ¥0.020124 |
| 明确 `ratio: 16:9` | 245,025 | ¥13.584186 | ¥13.584186 | ¥0 |

未指定比例时 actual 比估算多 363 tokens。最终任务账单仍按 245,388 tokens × ¥55.44/百万 = ¥13.604310 正确结算，误差不超过一个 raw quota；问题只在于“预扣一定覆盖最终费用”的硬约束被打破。

火山方舟当前创建视频任务 API 把 `ratio` 定义为可选，并说明部分 Seedance 系列默认 `adaptive`。结合本次显式 `16:9` 对照，合理推断本任务的波动来自默认自适应输出尺寸；但官方公开片段没有对本模型 ID 给出逐项计量解释，因此这仍是基于对照实验的推断，而不是官方结算承诺。官方参考：<https://api.volcengine.com/api-docs/view?action=CreateContentsGenerationsTasks&serviceCode=ark&version=2024-01-01>。

建议后续二选一：

1. 公司调用规范和网关都强制传入受支持的明确比例，并按比例补充真实用量矩阵；或
2. 保留 adaptive，但预扣按已验证的最大输出尺寸/安全余量计算。

在完成修复前，不应向业务承诺“余额绝不出现小额透支”；可以承诺最终费用按 actual 精确结算。

### 10.2 `EMP-DASHBOARD-001`：日志顶部历史用量恒为 0

**状态：FAIL（展示）；账本和日志明细 PASS。**

影响：管理员不能依赖通用日志页面顶部的“用量”卡看历史总额，应暂时使用 `/dashboard/users`、`/users` 和日志明细。修复范围很小，但本轮没有获得“修改该问题”的明确指令，因此只记录证据和原因。

### 10.3 `EMP-AGGREGATE-001`：退款未反向进入 `quota_data`

**状态：FAIL（极小聚合误差）；用户钱包/任务/渠道权威账本 PASS。**

员工 A：

```text
tasks 最终合计       15,289,543 raw = ¥30.579086
quota_data 聚合      15,289,571 raw = ¥30.579142
差异                        28 raw = ¥0.000056
```

差异恰好是 A 的 480p 退款。全局历史上已有另一笔同额 480p 退款，所以当前：

```text
全局 tasks/channel   123,608,712 raw = ¥247.217424
全局 quota_data      123,608,768 raw = ¥247.217536
差异                        56 raw = ¥0.000112
```

当前两位小数页面不会显示该差异，但长期累计退款后可能逐渐放大。权威账本应以 `tasks.quota`、用户 `used_quota` 和渠道 `used_quota` 为准；修复时需要让退款对 `quota_data` 做负向调整，或让看板直接使用净额数据源。

### 10.4 `EMP-TOKEN-INFO-001`：unlimited token 的 remain 为负

**状态：已解释，不是请求失败。**

### 12.4 本轮修复的验收脚本兼容性

最终复核时，`verify-local-compose.ps1` 首次在本机 Windows PowerShell 5.1 下误报 `Docker Compose returned invalid JSON`。Docker Compose 实际输出是合法 JSON，根因是脚本调用了 Windows PowerShell 5.1 不支持的 `ConvertFrom-Json -Depth` 参数；原回归测试还使用了同样不兼容的参数和 `utf8NoBOM` 编码枚举。

处理过程遵循红灯—绿灯：

1. 先让回归测试本身能在 Windows PowerShell 5.1 进入被测脚本；
2. 观察测试因被测脚本误报 JSON 失败，退出码 1；
3. 只移除不受支持的 `-Depth 100`，不改变 Compose 校验规则；
4. 把测试临时 YAML 的编码改为 Windows PowerShell 5.1 支持的 `UTF8`；
5. 重新运行回归测试和真实配置验证。

最终结果：

```text
PASS verify-local-compose behavior
PASS services
PASS pinned-images
PASS ports
PASS database-ledger
PASS local-http-boundary
```

代码位置：`scripts/verify-local-compose.ps1`；回归测试：`scripts/tests/verify-local-compose.tests.ps1`。这项修复只影响验收脚本兼容性，不重启容器、不修改数据库，也不访问付费上游。

## 14. 最终建议

建议把正式运营模型定为：

```text
公司 1 个火山方舟账号
        ↓
New API 1 个真实方舟渠道/Key
        ↓
每名员工 1 个普通用户账号
        ↓
每名员工 1 把只允许 Seedance 2.5 的虚拟 Key
        ↓
员工只拿 Base URL + Key；Root/管理员统一看全局页面
```

这个方案比“Root 下直接创建 20 把 Key”多一个用户对象，但换来了平台原生的用户级余额、全局用户排行、管理员查看边界和清晰的员工账本。对约 20 人规模，运维成本可控；后续真正值得开发的是批量开户/发 Key 脚本和上述三个已确认缺陷，而不是另造一套数据看板。
